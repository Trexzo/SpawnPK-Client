## Pathological exact-v308 class

The real blocker from #61 is `rs/d/a.class`, whose large static method is approximately
62,903 bytes of bytecode.

For a focused acceptance, the exact class from the R8A readable JAR was placed in an
isolated temporary JAR and passed through the exact Procyon whole-JAR invocation shape.

Result:

```text

elapsed:              00:11.18
max RSS:              592,500 KiB
generated file:       rs/d/a.java
generated bytes:      124,317
generated lines:      2,124

```

Checked R5A marker set:

```text
could not decompile

this method could not be decompiled

```

None occur in the generated pathological source.

This directly clears R8B's oversized-method acceptance target.

## Source-readiness safety

R5A already detects Procyon's known inline failure form:

```text
// This method could not be decompiled.
```

R8B adds an explicit regression test with `engine=procyon` proving that such output fails
static source readiness. A zero Procyon process exit therefore cannot silently bypass R5A.

## Full-archive observation

A full Procyon pass over the 10,472-class R8A readable archive was also started with a
4 GiB Java heap. The local execution harness terminated that run at 120 seconds after
approximately 79 Java files had been emitted.

That observation is not classified as a Procyon decompilation failure: stderr was empty and
the process was killed by the external harness timeout. It does show that whole-archive
R4C runtime may be the next practical end-to-end constraint and should be measured
separately after R8B lands rather than hidden inside this acceptance.

## Acceptance

R8B satisfies the decompiler-engine portion of #61:

- Procyon is a third explicit hash-pinned engine;
- CFR and Vineflower behavior remains intact;
- source-workspace/release/update-release surfaces accept `procyon`;
- no decompiler binary is vendored;
- the exact pathological v308 class decompiles successfully with no R5A failure marker;
- silent Procyon failure comments remain blocked by R5A.

The next step is the post-R8B exact-v308 R4C -> R5A/B/D/E run. Any new blocker found there
should be treated as empirical follow-up work rather than weakening existing gates.
