# R95 — strict original-v309 all-four nested enum acceptance

R47 established four original owner-nested enum JVM classes and a Java-source naming collision in the fourth. R49 reconstructed source prototypes for three normal enums and one flattened dollar-named workaround. The latter's JVM methods can match with enum-generated aliases, but its original nested InnerClasses metadata is absent or different. This is a **hard identity veto** and must not be counted as complete original nested-class recovery.

R95 adds a private whole-JAR-SHA-pinned gate requiring exactly four original AND candidate nested classfile entries under the same owner, one-to-one original binary class identities, and R49's existing strict normalized enum method/constant/field/exception comparisons for **all four**. In addition, it parses the original class-level InnerClasses attribute into constant-pool-resolved symbolic (inner class, outer class, inner source name, flags) records and requires complete ordered equality for each of the four JVM enum classfiles. Numeric constant-pool indices are intentionally not compared; symbolic identities, order and modifiers are.

A candidate made from the flat fourth-enum prototype must be rejected if its actual InnerClasses table differs. Four matches with R49's limited compiler-generated enum field/helper name aliases still do NOT prove alias-free original obfuscated names, authorial source, external helper implementation or runtime behavior.

The private CLI takes original JAR, candidate JAR, owner entry, new private output and both complete SHA256 pins. No accepted output is created unless all four enum and InnerClasses checks pass. Hosted Java 9 tests compile four real synthetic nested enums and verify all-four positive matching, failure on a missing fourth class, failure on flattened/missing metadata, and a changed method instruction. The actual original v309 binary was independently inspected read-only: exactly four nested JVM enums with ACC_ENUM/ACC_FINAL (one source-level name collision), but **no R95 replay against a recovered all-four Java candidate is claimed**. Original names, literal values, classfiles and private source remain outside GitHub.
## Independent original-v309 binary inventory (12 October 2026)

I verified the locally mounted exact-original complete JAR SHA-256 and independently enumerated its four owner-nested classfiles. Each is Java 9 **major 53**, has JVM `ACC_PUBLIC|ACC_FINAL|ACC_SUPER|ACC_ENUM` flags, and carries a real class-level `InnerClasses` attribute. Their four byte lengths, without identifying class names, are **960, 1010, 1039, 1165** bytes. An aggregate-only proof and noncertification flags are recorded at `research/v309-source-recovery/original-nested-four-innerclasses-evidence-r95.json`.

The four original binary files **have not** been compared by this generic R95 CLI against any single recovered four-enum Java candidate. The locally observed original bytes ground the need for symbolic nested metadata checking; they do not themselves prove reconstruction or runtime equivalence.

### Owner-side nested metadata (original v309)

Read-only `javap -v -p` of the pinned original 126-field settings owner additionally confirms **six** ordered class-level `InnerClasses` records: **four** referring to the original owner-nested enum classes and **two** referring to other nested classes. The R95 gate now verifies the outer owner's *entire ordered symbolic InnerClasses table*, in addition to each of the four nested classfile tables. A candidate that preserves all four enum method bodies and their own metadata but omits an outer-owner entry must fail closed. These are original-binary observations, not a completed source-recompilation or runtime-parity claim.
